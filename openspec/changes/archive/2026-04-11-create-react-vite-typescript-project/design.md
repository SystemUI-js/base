## Context

当前仓库仅包含 OpenSpec 变更文档，尚未建立可运行的前端工程。该变更的目标是在仓库根目录初始化一个基于 React + Vite + TypeScript 的前端项目，并同时补齐 ESLint、Prettier 与基础脚本，使后续需求可以直接在统一的工程约定上开发。

这个初始化动作同时覆盖工程结构、构建链路与代码质量工具，属于跨模块的基础设施变更。设计文档需要先明确目录约定、配置边界与工具协作关系，避免在后续实现阶段出现脚手架结构反复调整、格式规则冲突或开发命令不一致的问题。

相关能力来自提案中的两个能力项：

- `react-vite-typescript-app`：提供应用入口、源码目录、构建与开发运行能力。
- `code-quality-tooling`：提供 ESLint 与 Prettier 的集成方式，以及与 TypeScript/React 协同工作的规范基线。

## Goals / Non-Goals

**Goals:**

- 在仓库根目录建立一个可直接运行、构建的 React + Vite + TypeScript 工程骨架。
- 提供清晰且尽量最小化的初始目录结构，满足继续扩展页面、组件与静态资源的需要。
- 定义统一的开发脚本，包括启动、构建、代码检查与格式化入口。
- 集成 ESLint 与 Prettier，并明确两者职责边界，避免重复校验或规则冲突。
- 保持配置可维护，优先采用主流、稳定、低耦合的默认方案，减少后续升级成本。

**Non-Goals:**

- 不在本次初始化中引入路由、状态管理、UI 组件库、测试框架或请求层等业务能力。
- 不提供复杂的多环境配置、SSR、微前端或 monorepo 结构。
- 不预先抽象过多业务目录规范，仅提供支撑后续扩展的基础结构。
- 不绑定特定包管理器的锁文件策略，脚本层保持与常见 Node 包管理器兼容。

## Decisions

### 1. 使用 Vite 作为构建与开发服务器

- **决策**：采用 Vite 初始化 React + TypeScript 项目，而不是手动拼装 Webpack 或引入更重的框架。
- **原因**：Vite 在前端基础项目场景下具备更低的启动成本、更快的本地反馈速度和更少的配置负担，适合作为仓库的默认起点。
- **备选方案**：
  - Webpack：灵活但初始化与维护成本高，不适合当前“先建立统一基础工程”的目标。
  - Next.js：适合 SSR/全栈场景，但会引入额外约束，超出当前纯前端基础脚手架范围。

### 2. 使用 TypeScript 严格模式作为类型基线

- **决策**：启用 TypeScript，并以严格类型检查为默认方向构建配置。
- **原因**：当前仓库是从零开始搭建，越早确定严格类型边界，越能避免后续以 `any` 为中心的弱类型扩散，符合仓库对可维护性与设计原则的要求。
- **备选方案**：
  - 宽松 TypeScript 配置：接入更快，但会降低后续重构与协作质量。
  - 纯 JavaScript：初期门槛更低，但不符合该变更提案与仓库约束。

### 3. 目录结构保持轻量，但为扩展预留清晰入口

- **决策**：初始结构以 `src/main.tsx`、`src/App.tsx` 和基础样式/资源入口为核心，不预设复杂分层；如需额外目录，仅保留 `src/components`、`src/assets` 这类通用扩展位。
- **原因**：初始化阶段的重点是建立“可运行、可维护、可演进”的基础，而不是提前做业务架构。轻量目录能降低认知成本，同时避免未来真实业务结构与预设模板冲突。
- **备选方案**：
  - 预建完整分层（pages/services/hooks/store 等）：可读性看似更强，但当前没有业务上下文，容易形成过度设计。
  - 完全只保留单文件入口：虽然最简单，但不利于后续自然扩展。

### 4. ESLint 负责代码质量，Prettier 负责格式化

- **决策**：明确 ESLint 与 Prettier 的职责边界：ESLint 处理潜在问题、React/TypeScript 规则与最佳实践，Prettier 处理代码格式；通过兼容配置关闭冲突的格式类 lint 规则。
- **原因**：这是一套社区广泛验证的组合方式，能够减少规则重复和开发体验冲突，也方便将来在 IDE 和 CI 中复用同一套行为。
- **备选方案**：
  - 仅使用 ESLint 处理格式：配置更集中，但格式能力与生态兼容性不如 Prettier 稳定。
  - 仅使用 Prettier：可以统一格式，但不能覆盖 React/TypeScript 的语义与质量问题。

### 5. 采用面向开发流程的标准脚本命名

- **决策**：在 `package.json` 中定义 `dev`、`build`、`lint`、`format` 等标准脚本，并让脚本含义与主流前端项目保持一致。
- **原因**：统一脚本命名可以降低成员切换项目时的学习成本，也便于后续在 CI 或文档中引用。
- **备选方案**：
  - 使用自定义脚本名：表达更具体，但不利于通用工具与团队习惯接入。
  - 只保留最小脚本集：实现简单，但会把格式化等常用行为转移到口头约定。

### 6. 示例页面仅承担“验证初始化成功”的职责

- **决策**：提供一个极简示例页面，用于验证 React 挂载、样式引入和 TypeScript 编译链路正常，不加入额外业务组件或演示逻辑。
- **原因**：示例页面的价值在于证明脚手架可用，而不是成为后续业务模板。越简单，越容易被后续真实页面替换。
- **备选方案**：
  - 使用 Vite 默认示例页面：可直接复用，但通常包含品牌化演示内容，不适合作为仓库长期基础模板。
  - 完全不提供页面：初始化更精简，但缺少对入口链路的直观验证。

## Risks / Trade-offs

- [基础结构过轻，后续业务接入时仍需调整目录] → 通过只约束入口与通用扩展位，降低未来重构成本，而不是现在一次性定死业务结构。
- [ESLint 与 Prettier 配置冲突导致开发体验差] → 明确职责边界，并使用兼容配置关闭格式类冲突规则。
- [TypeScript 严格配置提升初期接入门槛] → 通过保持示例代码简单、类型定义清晰来降低理解成本，换取后续可维护性。
- [未引入测试框架导致初始化后仍需补基础设施] → 本次将测试能力定义为非目标，避免把简单脚手架初始化扩展成过大范围变更。
- [不同包管理器可能带来锁文件和命令差异] → 先统一 `package.json` 脚本接口，不在本次设计中绑定单一锁文件策略。

## Migration Plan

1. 在仓库根目录新增前端工程基础文件，包括 `package.json`、TypeScript 配置、Vite 配置、ESLint/Prettier 配置与 `src/` 目录。
2. 安装提案所需依赖并验证开发、构建、lint、format 脚本可执行。
3. 使用极简示例页面确认入口渲染、样式加载与 TypeScript 编译链路正常。
4. 在后续实现阶段补齐对应 specs 与 tasks，使变更具备完整的实施与验收依据。

回滚策略：如果初始化结果不符合预期，可直接移除新增的基础工程文件并恢复仓库为仅包含 OpenSpec 文档的状态；由于当前仓库尚无业务代码，不涉及数据迁移与兼容性回滚问题。
