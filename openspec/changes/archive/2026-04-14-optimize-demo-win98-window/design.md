## Context

当前 Demo 首页以“工作台”形式同时展示主窗口、辅助窗口、模式切换、摘要指标和日志反馈，重点更偏向交互编排而不是 Window 能力本身。这与本次变更希望首屏聚焦为“单一 Win98 主题窗口展示”的目标不一致，也让默认入口承担了过多演示职责。

本次设计需要在不改变技术验证目标的前提下，收敛默认首页结构：

- 继续通过 `@system-ui-js/base` 的公开导出渲染窗口相关能力。
- 将默认入口从多状态、多面板场景调整为单窗口静态展示。
- 保留足够的排版内容，证明窗口容器、标题栏和内容区在 Demo 首屏可被直观感知。

受影响的实现主要集中在 `src/App.tsx` 和 `src/styles/app.css`，不涉及包发布链路、依赖升级或底层组件实现改动。

## Goals / Non-Goals

**Goals:**

- 将默认首页调整为单一的 Win98 主题窗口，突出首屏视觉焦点。
- 移除与当前目标无关的运行模式、摘要面板、日志区和辅助窗口等复杂交互。
- 通过少量静态文字内容保留对标题、段落和窗口承载能力的展示。
- 保持 Demo 仍然经由 `@system-ui-js/base` 公共 API 验证基础包导出的可用性。

**Non-Goals:**

- 不新增新的窗口能力、拖拽能力或复杂交互组件。
- 不修改 `@system-ui-js/base` 或底层主题实现。
- 不调整 Demo 构建方式、产物结构或部署流程。
- 不为首页继续保留多窗口协作式工作台体验。

## Decisions

### 1. 将首页重构为无状态的单窗口展示组件

`src/App.tsx` 中现有的 `useState`、`useMemo`、`useRef` 与模式切换、任务切换、日志刷新逻辑将被整体移除，页面退化为以静态内容为主的展示型组件。

这样做的原因是当前默认入口的复杂状态并不服务于“展示一个 Win98 主题窗口”这个核心目标，反而让视觉和认知焦点分散。用无状态结构替代后，代码也会更贴近 Demo 首页的真实职责：展示基础能力，而非模拟操作台。

备选方案是保留部分按钮交互，例如“切换模式”或“刷新摘要”，但这会继续引入额外状态、文案和布局空间，与收敛展示面的目标冲突，因此不采用。

### 2. 保留 `BaseThemeProvider` 与单个 `BaseWindow` 作为首屏唯一主体

页面仍保留 `BaseThemeProvider theme="win98"` 和一个主 `BaseWindow`，以确保 Demo 默认入口继续验证 Win98 主题与窗口组件组合是否可正常渲染。

主窗口将承载完整首屏内容，包括标题栏、说明文案和少量静态段落/列表，不再渲染第二个 Inspector 窗口，也不再保留桌面式多窗口层叠结构。

备选方案是改为普通页面容器中嵌入窗口片段，但这会削弱“默认入口就是窗口场景”的表达，因此不采用。

### 3. 将内容区调整为轻量的静态排版块，而不是仪表盘式面板

窗口内容区将使用简化后的排版结构，例如导语、说明段落和简短特性列表，重点展示：

- 这是一个通过 `@system-ui-js/base` 渲染的窗口演示；
- Demo 默认场景的职责是聚焦展示基础窗口外观；
- 内容布局在 Win98 主题下仍具备可读性与层次感。

备选方案是保留指标卡片、任务列表等内容块但去掉交互，这仍然会保留“工作台”语义，不符合提案中的收敛方向，因此不采用。

### 4. 样式层同步收敛为单窗口居中展示

`src/styles/app.css` 将从当前围绕工作区、辅助窗和面板细节的样式，收敛为服务单窗口布局的最小集合：

- 页面背景与舞台容器；
- 单窗口的定位或居中对齐；
- 内容区排版、间距与文本层级；
- 适度的响应式约束，避免窗口在较窄视口中溢出。

备选方案是保留现有桌面背景和绝对定位窗口坐标，仅隐藏多余模块，但这会留下大量无效样式和布局假设，不利于后续维护，因此不采用。

### 5. 持续限定为公共 API 验证路径

实现中仍只从 `@system-ui-js/base` 导入 `BaseThemeProvider`、`BaseWindow`、`BaseWindowTitle`、`BaseWindowBody` 等公开能力，不回退到深层实现或直接引用底层主题库。

这样能够保证 Demo 首页即便变得更简单，仍然具备对外导出面的回归验证价值。备选方案是为简化布局而绕过基础包封装，但这会削弱该 Demo 的验证意义，因此不采用。

## Risks / Trade-offs

- [风险] 页面过于静态后，可能被误解为演示能力变少。 → 缓解：在文案中明确说明该首页用于聚焦验证窗口主题与基础承载能力，而不是覆盖全部交互场景。
- [风险] 去掉绝大多数状态逻辑后，未来若想恢复复杂演示，可能需要重新组织页面。 → 缓解：将本次变更限定为默认首页收敛，不影响后续新增独立演示入口或其他场景页面。
- [风险] 单窗口居中布局在小屏幕上可能出现窗口尺寸不合适的问题。 → 缓解：为窗口宽度和舞台容器增加响应式约束，优先保证内容可见与可滚动。
- [风险] 删除旧样式时可能误伤仍被保留的窗口基础样式。 → 缓解：以 `App.tsx` 最终保留的类名为基准清理 CSS，并在完成后执行针对 Demo 入口的验证。

## Migration Plan

1. 精简 `src/App.tsx`，移除多窗口、多状态与多面板逻辑，只保留单窗口与静态内容。
2. 重写 `src/styles/app.css`，删除 Inspector 和仪表盘相关样式，补齐单窗口展示所需的布局与排版样式。
3. 运行 Demo 相关验证，确认默认入口仍可构建并正确渲染 Win98 主题窗口。
4. 若效果不符合预期，可直接回滚 `src/App.tsx` 与 `src/styles/app.css` 到变更前版本，不涉及数据迁移或依赖回退。

## Open Questions

- 暂无阻塞性开放问题；若后续需要保留“更多演示场景”入口，应通过新增独立页面或路由解决，而不是继续扩张默认首页职责。
