## Context

当前仓库仍是单一的 React + Vite + TypeScript 初始化工程：根目录 `package.json` 仅覆盖应用开发脚本，`src/main.tsx` 负责 Demo 入口，`src/App.tsx` 仍为占位页面，尚未形成可发布的 `@system-ui-js/base` 包入口、构建产物边界与对外导出面。

本次变更需要同时满足两类交付目标：

- 对外发布 `@system-ui-js/base` 包，作为后续基础能力沉淀的载体。
- 提供一个可独立构建和部署的 Demo 站点，用于集成 `@system-ui-js/chameleon` 并展示首个 Window 场景。

约束条件如下：

- 尽量在现有单仓结构上演进，避免在首个变更中引入过重的多包治理成本。
- 包构建与 Demo 构建必须可分离执行，避免发布包时夹带展示站产物。
- Demo 需要尽可能复用对外公开的包入口，避免“Demo 可运行但包能力未被验证”的分叉。

## Goals / Non-Goals

**Goals:**

- 建立同时支持库产物与 Demo 产物的工程结构与构建流程。
- 明确 `@system-ui-js/base` 的公开入口、产物目录、依赖边界与发布方式。
- 让 Demo 站点接入 `@system-ui-js/chameleon` 并落地首个 Window 展示页面。
- 保证后续新增基础能力时，可以沿用同一套包导出与 Demo 验证路径持续扩展。

**Non-Goals:**

- 不在本次变更中引入完整 monorepo 拆分或多应用编排体系。
- 不一次性建设完整组件站点、文档系统或多页面导航框架。
- 不在本次变更中覆盖 Window 之外的完整组件能力矩阵。
- 不处理 npm 发布流水线、版本发布自动化等后续工程化议题。

## Decisions

### 1. 采用“单仓双目标”结构，而不是立即拆成 monorepo

保留当前仓库为单一 package，新增库入口与独立构建脚本，让根工程同时承担包发布与 Demo 展示两种职责。

- 库侧新增公开入口文件，用于承载 `@system-ui-js/base` 的导出面。
- Demo 侧继续保留应用入口，但页面实现迁移为真实展示场景，而非占位内容。
- 构建脚本按目标拆分为库构建与 Demo 构建，顶层 `build` 负责聚合执行。

这样可以在当前阶段用最小改动获得可发布产物与可演示页面，同时避免过早引入 workspace、跨包依赖和额外发布编排。

备选方案：

- **立即拆成 `packages/base + apps/demo` 的 monorepo**：边界更清晰，但当前仓库能力尚少，引入目录迁移、工具链重配与开发链路调整的成本偏高。
- **仅保留 Demo，不建设包入口**：实现更快，但无法满足“形成可发布基础包”的核心目标。

### 2. 库构建与 Demo 构建使用分离配置和分离产物目录

构建层面采用双目标配置：

- Demo 构建继续使用 Vite 应用模式，输出面向站点部署的静态资源。
- 库构建使用 Vite 的 library mode 配合 TypeScript 声明产物输出，生成面向 npm 包发布的 JavaScript 与类型文件。
- 两类产物进入不同目录，避免互相污染，并通过 `package.json` 的 `files` / `exports` 约束发布内容。

选择分离配置而不是在单个配置文件内通过复杂分支切换，是为了降低维护成本并让每个目标的输入、输出与 external 策略更直观。

备选方案：

- **单一 Vite 配置通过 mode 切换**：文件更少，但配置分支会随着库与 Demo 差异扩大而迅速变复杂。
- **改用额外打包工具（如 tsup / rollup 组合）**：灵活性更高，但在首个变更中会引入额外学习与维护成本。

### 3. 依赖边界以“React 外置、Chameleon 运行时依赖”建模

`react` 与 `react-dom` 作为基础运行时，应在库构建中保持 external，并在包元数据中以 peer dependency 为主、开发依赖为辅，避免重复打包 React。

`@system-ui-js/chameleon` 作为 `@system-ui-js/base` 的底层组件基础，优先建模为运行时依赖，由基础包统一管理版本，以降低使用方接入第一个版本时的装配成本。Demo 与库共用同一套 Chameleon 版本，减少展示结果与对外交付行为不一致的问题。

备选方案：

- **将 `@system-ui-js/chameleon` 设为 peer dependency**：可提升宿主控制权，但会增加接入门槛，并让首个版本的安装与演示路径更易出错。

### 4. Demo 页面通过公共导出面驱动展示，而不是深层直接引用实现文件

Window Demo 的页面层可以保留自身布局与场景编排代码，但其使用的基础能力应优先从 `@system-ui-js/base` 的公共入口导入，确保 Demo 同时承担“使用示例 + 包导出面验证”双重角色。

必要时可在基础包内部增加轻量封装层，用来屏蔽 `@system-ui-js/chameleon` 的原子 API，避免 Demo 与未来业务方直接依赖底层细节。

备选方案：

- **Demo 直接引用 `src` 内部实现文件**：开发速度更快，但会绕过公共 API，削弱发布包的验证价值。

### 5. 样式按“库内可复用”与“Demo 专属展示”分层

当前样式均由应用入口直接加载。变更后需要拆分为两层：

- 基础包侧仅保留组件运行所必需的样式、token 或封装过的主题接入点。
- Demo 侧承载页面布局、展示背景、示例排版等站点专属样式。

这样可以避免 Demo 的展示性样式泄漏到 npm 包中，也能为未来扩展更多示例场景保留清晰边界。

## Risks / Trade-offs

- **[单仓双目标导致配置增加]** → 通过独立构建脚本、独立输出目录和清晰命名降低理解成本。
- **[Demo 既是站点又承担包验证职责，耦合度上升]** → 通过公共入口导入约束与目录分层，把耦合控制在“验证发布面”这一必要范围内。
- **[`@system-ui-js/chameleon` API 若仍在演进，基础包可能频繁调整]** → 在基础包内部增加适配层，优先暴露稳定语义接口，减少对底层 API 的直接扩散。
- **[类型声明、导出字段与实际产物可能不一致]** → 在实现阶段补充针对构建产物的校验步骤，确保 `exports`、声明文件与输出目录同步。

## Migration Plan

1. 调整根目录包元数据与脚本，补齐基础包命名、入口、发布文件范围和依赖声明。
2. 增加库入口与相关源码组织，明确对外导出面。
3. 为 Demo 与库分别配置构建路径，确保两类产物可以独立生成。
4. 接入 `@system-ui-js/chameleon`，完成 Window Demo 首屏展示。
5. 运行库构建与 Demo 构建验证产物边界，再进入后续任务实现。

当前变更尚未发布到外部环境，因此不存在数据迁移问题；若实现过程中需要回滚，可直接撤销新增构建配置与包入口，恢复为单纯的 Vite 应用骨架。

- Demo 站点最终是仅用于本地验证，还是需要预留静态托管部署路径与资源基准路径配置？
